# Deploy previews: what this branch does, and what is still missing

Working note for the `feat/deploy-preview-auth` branch. The durable reference is
[`docs/deploy.md`](docs/deploy.md) → *Preview deployments*; this file is the status of the change
and the list of things a human with Netlify, Neon and Google access still has to do.

**State:** the code side is done and verified locally. The platform side — Netlify env vars, a
Neon branch, previews enabled — is untouched, because none of it lives in this repo.

---

## 1. The problem

A Netlify deploy preview gets a fresh URL per pull request
(`deploy-preview-42--<site>.netlify.app`). Two independent things broke on that:

1. **Sign-in.** Google matches OAuth redirect URIs exactly and allows no wildcard, so a preview's
   callback URL can never be registered. `NEXTAUTH_URL` also pinned the app to one origin.
2. **The build.** `build:deploy` is `prisma migrate deploy && next build`, so a preview holding
   production's `DATABASE_URL` would have migrated **production** on every pull request.

Nothing about the app's own behaviour changed: same session shape, same `/api/auth/callback/google`
path, so **the existing Google OAuth client needs no new entry**.

## 3. How sign-in on a preview works now

Set `AUTH_REDIRECT_PROXY_URL=https://<production-host>/api/auth` on *every* context. The deployment
whose own origin matches that URL is the one that forwards.

1. The preview sends the user to Google naming **production's** callback as `redirect_uri`, with the
   OAuth `state` carrying its own callback URL (encrypted with `NEXTAUTH_SECRET`).
2. Google returns the code to production, which decodes the state, sees an origin that is not its
   own, and 302s the whole callback — code and state intact — to the preview.
3. The preview verifies its own `state` cookie, exchanges the code (again naming production's
   `redirect_uri`, which is what Google issued it for) and sets its own session cookie on its own
   domain.

Local dev leaves `AUTH_REDIRECT_PROXY_URL` unset and uses the ordinary direct flow.

## 4. What was verified, and how

Two `next start` instances off one build, `:3411` standing in for production, `:3412` for a preview,
same secret, `AUTH_REDIRECT_PROXY_URL=http://localhost:3411/api/auth` on both:

- the preview's authorize redirect carried production's callback as its `redirect_uri`
  (`http://localhost:3411/api/auth/callback/google`), not its own;
- that callback delivered to `:3411` came back as a `302` to
  `http://localhost:3412/api/auth/callback/google?code=…&state=…`;
- the same callback delivered to `:3412` did **not** forward (it is not the proxy) — the control;
- a cookie minted by `scripts/session-cookie.ts` is accepted by the v5 server: `/api/auth/session`
  returned `{"user":{"email":"smoke@example.com","id":"u1","role":"admin"}}`, so the smoke suites'
  cookie name and salt are right;
- `npm run typecheck` clean, `npm run lint` at its two pre-existing `exhaustive-deps` warnings,
  `npm run build` exit 0, `npm ci` installs the lockfile from npmjs.

## 5. What was NOT verified

- **The smoke suites never ran.** The worktree has no `.env`, so no `DATABASE_URL`. Run them against
  a scratch database before merging: `npm run auth:smoke`, `entities:smoke`, `base44:smoke`,
  `sunny:smoke`, `market:smoke`, `rls:smoke`.
- **No real Google round trip.** The handshake was proved with a fake `code`; nothing in the local
  test talked to `accounts.google.com`.
- ~~**No real Netlify deploy.**~~ **Settled, and it failed.** Netlify serves the alias
  `deploy-preview-N--<site>.netlify.app` with a `200` but hands the server handler the deploy
  permalink `<deploy-id>--<site>.netlify.app` in `host` / `x-forwarded-host`. Measured on two live
  previews: `/api/auth/providers` on PR #24's alias reported the permalink as its own callback URL.
  A preview therefore named the permalink as its forwarding target while the browser held the
  host-only `state` cookie on the alias, and sign-in died as
  `InvalidCheck: state value could not be parsed` — which is also what a *missing* cookie reports,
  since `parseCookie` in `@auth/core` rewrites every cause into that string.

  Fixed by pinning `AUTH_URL` to `DEPLOY_PRIME_URL`; see the `next.config.ts` row in §2. Verified
  locally by building with `DEPLOY_PRIME_URL=http://pinned-alias.example`, serving it, and sending
  a request with `Host: 6a97fdd1--permalink.netlify.app`: the decoded OAuth `state` carried
  `origin: http://pinned-alias.example/api/auth/callback/google`, the pinned value, not the host.

  Still unproven on a real deploy: that `DEPLOY_PRIME_URL` is present in Netlify's *build*
  environment for preview contexts. It is documented to be, and the build-time bake is why it does
  not also need to be in the runtime environment — but the first preview deploy after this change
  is what confirms it. If a preview's `/api/auth/providers` still reports the permalink, the bake
  came out empty.

## 6. Still required

### Netlify → Site configuration → Environment variables

Scope matters as much as value. Netlify lets each variable carry a different value per context;
`NEXTAUTH_URL` must be **absent** from the preview contexts, not merely different.

| Variable | Production | Deploy previews + branch deploys |
| --- | --- | --- |
| `AUTH_REDIRECT_PROXY_URL` | `https://<production-host>/api/auth` | **same value** |
| `NEXTAUTH_SECRET` | as today | **the same secret** |
| `NEXTAUTH_URL` | `https://<production-host>` | **unset** |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | as today | same client |
| `DATABASE_URL`, `DIRECT_URL` | production Neon | the **preview Neon branch** |
| `NEXT_PUBLIC_BASE44_APP_HOST` | as today | same value |
| `BASE44_SVC_KEY`, `BASE44_ORG_ID`, `BASE44_PLATFORM_HOST`, `BASE44_APPS_FOLDER_ID` | as today | optional — see §7 |

Then confirm **Build & deploy → Deploy Previews** is enabled for pull requests — it is what
produces the `deploy-preview-N` URLs the proxy forwards to.

### Neon

1. Create a branch of the production database (Neon branches are copy-on-write and instant).
2. Put its pooled URL in `DATABASE_URL` and its direct URL in `DIRECT_URL`, scoped to the preview
   contexts only.
3. Because previews never migrate, apply schema changes to that branch yourself whenever a pull
   request adds a migration:

   ```bash
   DATABASE_URL=<preview branch pooled> DIRECT_URL=<preview branch direct> npm run db:deploy
   ```

Without `DATABASE_URL` a preview cannot even build — `prisma generate` fails schema validation in
`postinstall`.

### Google Cloud console

**Nothing to add** — that is the point of the proxy. Two caveats:

- While the OAuth consent screen is in **Testing**, only listed test users can sign in, on previews
  as much as on production.
- The redirect URI already registered (`https://<production-host>/api/auth/callback/google`) is now
  load-bearing for previews too; changing it breaks both at once.

### After the first preview deploys

Sign in on the preview URL in a browser and confirm the address bar comes back to
`deploy-preview-N--<site>.netlify.app`, not to production.

Note that `/api/auth/providers` is **not** the way to check: it reports the deployment's own
callback URL either way (verified locally). What shows the proxy is live is the `redirect_uri` on
the authorize redirect, which should be production's:

```bash
P=https://deploy-preview-42--<site>.netlify.app
T=$(curl -s -c /tmp/j "$P/api/auth/csrf" | python3 -c 'import sys,json;print(json.load(sys.stdin)["csrfToken"])')
curl -s -D- -o /dev/null -b /tmp/j -X POST --data "csrfToken=$T" "$P/api/auth/signin/google" | grep -i '^location:'
```

## 7. Decisions still open

- **A preview deploy is production-equivalent trust.** The proxy requires previews to hold
  production's `NEXTAUTH_SECRET`, and that secret also signs `/api/sunny` viewer tokens — so a
  preview can mint tokens production accepts. Anyone who can open a pull request can run code with
  that secret. If that is not acceptable, the alternative is a second Netlify site plus a second
  Google client acting as its own proxy for previews, at the cost of a separate secret to rotate.
- **Built apps in a preview still call production's `/api/sunny`.** The `sunny-platform` skill
  lives in the Base44 workspace and hardcodes one host (`docs/sunny-platform-skill.md`,
  `<SUNNY_HOST>`), so an app in a preview reads and writes **production** rows — scoped to
  its viewer, but production data all the same. Making it follow the deployment means a
  per-environment skill, or teaching the builder instructions to inject the shell's own origin.
- **Base44 keys on previews or not.** Without them a preview shows the builder's "Connect" state and
  everything else works. With them, previews share the production workspace and apps folder, so apps
  built in a preview land in production's folder. Per-user service principals are safe either way:
  provisioning is idempotent on the email-derived `service_external_id`
  (`src/lib/base44Link.ts`), so a preview reuses the principal that user already has.
- **`next-auth` v5 is still beta** (`5.0.0-beta.32`). It is what ships the redirect proxy; v4 has no
  equivalent, since its OAuth `state` is an opaque random value with nowhere to carry an origin.

## 8. Rollback

Everything is contained in this branch. `git revert` it (or drop the branch) and previews go back to
being off: production keeps signing in exactly as before, because its own flow never uses the proxy
branch of the code.
